  - **Bug found via actual use, 2026-09-21**: exactly the gap the caveat above warned about — the user reported that picking a result from the Flutter combobox didn't populate the input at all, on every call site. Two fixes, in order:
    1. `8a2af9f` — a real but, it turned out, unreachable bug: `_pick()`/`_createNew()` set the text then called `unfocus()`, whose focus listener would revert it back to the stale `widget.selectedLabel` prop. Fixed with a `_suppressBlurRevert` flag. Didn't resolve the report.
    2. `2729cbe` — **the actual root cause**: `TextField` defaults `onTapOutside` (desktop platforms only) to firing `unfocus()` on the raw `PointerDownEvent`, for any tap outside its own `TapRegion`. The results panel lives in a separate `Overlay`, so every click on a row counted as "outside" — `unfocus()` closed the panel on pointer-*down*, before the tap gesture could resolve into `onTap` on pointer-*up*. The row was gone from the tree by the time `_pick()` would have run, on every instance, which is why it looked identical everywhere: this is the only combobox variant in the app backed by a real `TextField` (`AppSelectField`/`AppMultiSelectField` use a plain `GestureDetector` trigger and were never affected). Fixed with `onTapOutside: (_) {}` — the existing full-screen `GestureDetector` in `_openPanel()` already handles "click elsewhere closes it" correctly, as a real resolved tap rather than a raw pointer-down race. Both fixes are needed together (the panel now stays put long enough for `_pick()` to run, and `_pick()` no longer gets its own text reverted right after).
    Web's `gwSearchableSelect` doesn't share either bug (plain JS, no TextField/TapRegion/FocusNode semantics at all) — checked, not just assumed.
    **Lesson for next time**: this diagnosis took two attempts because the first fix was based on reading the code, not on reproducing the failure — should have asked "does the panel even receive the click" before assuming the click succeeded and something downstream undid it.
